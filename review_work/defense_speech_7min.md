## Текст выступления

Здравствуйте, уважаемые члены комиссии. Меня зовут Пыхтин Дмитрий. Тема моей выпускной квалификационной работы - разработка веб-приложения SysAssist для автоматизации обработки ИТ-инцидентов и управления регламентированными действиями в инфраструктуре предприятия.

Главная идея проекта состоит не в том, чтобы заменить существующие системы мониторинга, а в том, чтобы связать их с рабочим процессом инженера. Мониторинг может быстро показать проблему, например недоступность сервиса, ошибку базы данных или перегрузку контейнера. Но после этого обычно начинается ручная часть: нужно понять, кто отвечает за реакцию, какое действие безопасно, требуется ли согласование и где потом найти доказательства, что именно было сделано. В реальной эксплуатации эти сведения часто расходятся по чатам, логам, дашбордам и ручным таблицам.

Именно эту проблему решает SysAssist. Система выступает как координационный слой между событиями инфраструктуры, регламентированными действиями, ролями пользователей и аудитом. Она принимает или получает событие, приводит его к единой модели, связывает с модулем, предлагает действие, проверяет риск, при необходимости отправляет действие на согласование и сохраняет результат в журнале.

Цель дипломного проекта - разработать и обосновать SysAssist как локально разворачиваемую платформу для обработки ИТ-инцидентов. Под разработкой в работе понимается не только интерфейс, а вся основа приложения: backend, frontend, база данных, API, роли пользователей, модульный каталог, безопасность, диагностика и проверка готовности к запуску.

Объектом исследования является процесс сопровождения корпоративных информационных систем, а предметом - программная реализация SysAssist, которая поддерживает этот процесс средствами веб-приложения, базы данных, модульных адаптеров и ролевой модели.

Технически проект построен на современном, но достаточно строгом стеке. Серверная часть реализована на .NET 9, C# и ASP.NET Core Minimal API. Клиентская часть выполнена на React, TypeScript и Vite. В качестве базы данных используется CockroachDB через EF Core и Npgsql. Архитектура разделена на несколько проектов: Domain, Application, Contracts, Infrastructure, Api и Web. Такое разделение нужно не для формальности, а для того, чтобы доменная модель, контракты, инфраструктурная реализация и пользовательский интерфейс не смешивались между собой.

В центре системы находится модель инцидента. Событие сохраняется как IncidentEvent: у него есть источник, тип, серьезность, целевой объект, статус, payload и correlation id. Отдельно хранится EventRecommendation, то есть рекомендация по событию. Это важно, потому что факт события и мнение системы о возможном действии не смешиваются в одну запись.

В проекте реализован модульный каталог. В базовой поставке описано 13 модулей: Zabbix, Grafana, Prometheus Alertmanager, PostgreSQL, Redis, Docker, Nginx, Linux Host, HTTP Endpoint Checker, File System Monitor, SMTP Email, Telegram Bot и Local Rule Advisor. Для модулей предусмотрены настройки, health checks, признаки SafeMode и fallback, а также каталог действий. Всего в каталоге 65 remediation actions, но в дипломе отдельно подчеркивается: наличие действия в каталоге не означает, что его можно безусловно выполнять в продуктивной среде.

Ключевой сценарий работы выглядит так. Событие поступает через webhook, polling или демонстрационный сценарий. SysAssist нормализует его, сохраняет в базе, создает рекомендацию и определяет возможное действие. Если действие низкорисковое и модуль здоров, инженер может выполнить его в рамках прав. Если действие относится к высокому риску или требует подтверждения, система создает approval request. Решение принимает пользователь с соответствующей ролью, например SeniorAdmin или Admin.

Безопасность в проекте реализована несколькими слоями. Первый слой - JWT-аутентификация. Второй - RBAC, то есть разграничение прав по ролям. Третий - approval workflow для рискованных действий. Четвертый - SafeMode. Если SafeMode включен, даже одобренное действие не меняет внешнюю инфраструктуру, а фиксируется как заблокированное или симулированное. Это важно для демонстрации и пилотного запуска, потому что можно показать весь маршрут решения без риска повредить внешний сервис.

Отдельное внимание уделено секретам и аудиту. Секретные настройки модулей шифруются с помощью AES-GCM, а в ответах API возвращаются только маскированные значения. Support bundle собирает материалы для разбора проблемы: состояние модулей, health checks, инциденты, рекомендации, согласования, действия, audit, logs, notifications и diagnostics. При этом password hashes, raw secrets, JWT keys и license tokens не должны попадать в выгрузку.

Для эксплуатации в проекте предусмотрены health endpoints и Production Readiness Gate. Это не просто чек-лист в документации, а отдельный API-механизм, который проверяет конфигурацию и runtime-состояние: отключен ли demo data, настроены ли AllowedHosts и CORS, есть ли сильный JWT secret, задан ли encryption key, валидна ли лицензия, доступна ли CockroachDB, свежая ли диагностика, здоровы ли включенные модули, отключен ли fallback и включен ли SafeMode.

Развертывание описано в двух вариантах. Локальный docker-compose подходит для лабораторной проверки и демонстрации. Production-shaped compose устроен иначе: база данных вынесена наружу, миграции выполняются отдельным контейнером, API не публикуется напрямую, а frontend работает через web/reverse-proxy entrypoint. В работе это не подается как доказанное промышленное внедрение. Корректнее говорить, что проект готов для controlled demo и пилотного разворачивания, но для промышленной эксплуатации требует реальных секретов, TLS, мониторинга, бэкапов, security audit и настройки внешних интеграций.

Проверка проекта выполнялась на уровне кода, документации и тестов. В тестах проверяются безопасность, шифрование секретов, лицензирование, маскирование данных, approval workflow, SafeMode, support bundle и запрет ложного успеха, если модуль не имеет здорового реального подключения. Также подготовлен smoke-скрипт, который проверяет readiness, login, dashboard, modules, diagnostics, production readiness, logs и support bundle уже на запущенном контуре.

Итоговый результат работы - не просто интерфейс, а связная платформа обработки ИТ-событий. В ней есть backend, frontend, CockroachDB-хранилище, EF Core-модель, ролевой доступ, модульный каталог, approval workflow, SafeMode, audit trail, support bundle, production readiness gate и тесты.

При этом в работе честно обозначены ограничения. Проект не заявляется как полностью внедренная промышленная система. Часть интеграций требует реальных внешних настроек, SSO/OIDC и refresh-token lifecycle остаются направлением развития, immutable audit sink и расширенная provider-specific webhook signature validation также относятся к следующему этапу.

Таким образом, цель дипломного проекта достигнута: SysAssist разработан и описан как веб-приложение для автоматизации обработки ИТ-инцидентов и управления регламентированными действиями. Практическая ценность проекта состоит в том, что он показывает полный маршрут события: от поступления и диагностики до согласования, безопасного выполнения или блокировки, аудита и подготовки доказательной базы.
